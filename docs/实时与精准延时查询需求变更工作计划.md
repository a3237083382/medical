# 实时与精准延时查询需求变更工作计划

> 日期：2026-08-13  
> 需求来源：保险公司查询服务模式调整  
> 关联页面：`RuoYi-Vue3/index.html`、保险公司嵌入式查询页、后台日志管理页、人工结果上传页参考图  
> 当前状态：计划阶段，尚未进入编码

---

## 1. 需求变更摘要

平台面向保险公司提供两种查询服务：

| 服务 | 面向对象 | 查询方式 | 返回时机 | 数据处理 | 费用定位 |
| ---- | -------- | -------- | -------- | -------- | -------- |
| 实时数据查询 | 保险公司 | 后台同步调用数产集团接口 | 立即返回 | 原样返回数产集团给到的数据，不做加工 | 较低 |
| 精准延时数据查询 | 保险公司 + 平台管理/运营人员 | 保险公司提交姓名、身份证后生成待处理请求，由平台管理/运营人员人工查询本公司数据并上传结果 | 上传完毕后返回给保险公司查看 | Excel 导入或逐行录入，保存前可修改 | 较高，数据更详细 |

本次变更的重点不是继续做旧的“历史库同步查询”，而是新增一条“延时请求工单”流程：保险公司提交请求后可以退出页面，平台管理/运营人员看到待处理请求并上传结果，保险公司后续回到页面或刷新记录时看到结果已完成。

---

## 2. 当前基线

已存在能力：

- 保险公司端已有嵌入式查询入口和查询类型接口：`/company/embed/medical/query-types`、`/company/embed/medical/query`。
- 后台已有通用查询日志页面：`/business/query-log`。
- 后台已有历史数据 Excel 导入页面和导入服务：`/business/data-import`。
- 后端已有实时查询服务 `MedicalQueryServiceImpl`，当前逻辑会调用数据源、做历史缓存、做脱敏后返回。
- 已有月度预算、公司级价格、查询日志、费用流水等计费基础。

需要调整的关键点：

- 实时查询：由“脱敏/加工后返回”调整为“数产集团给什么就返回什么”。
- 非实时查询：由“同步查历史库返回”调整为“提交请求、人工处理、结果上传、保险公司异步查看”。
- 日志：由单一查询日志扩展为按公司查看实时查询日志和精准延时查询日志。

---

## 3. 明确假设

1. “精准延时数据查询”不要求保险公司在提交页面等待结果。
2. 保险公司提交姓名和身份证后，系统立即返回“已提交/待处理”的状态和请求编号。
3. 平台管理/运营人员处理请求时，可以上传 Excel，也可以在页面中逐行新增结果数据。
4. Excel 导入后的明细必须可编辑，编辑确认后才允许标记“上传完毕”。
5. “查询状态”用于表示内部是否已经完成人工查询，取值为“未查询/已查询”。
6. “结果上传”用于表示是否已有可给保险公司查看的结果，取值为“未上传/已上传”。
7. 特殊情况允许上传空结果，但需要给保险公司返回说明信息，例如“已查询到参保线索，但当前无可返回明细”。
8. 实时查询仍需记录日志和计费；精准延时查询至少需要记录提交日志、处理日志、上传完成日志，计费触发点需在开发前确认。

## 4. 方案选择

### 方案 A：复用旧 `history_medical` 同步查询

优点：改动最少，可以复用现有历史数据查询和导入能力。  
缺点：无法满足“保险公司可退出页面、内部处理完再显示”的核心流程，也难以表达未查询、已查询、未上传、已上传等状态。  
结论：不采用。

### 方案 B：新增精准延时查询请求表和人工处理台

优点：业务状态清晰，保险公司体验符合需求，后台可以按请求逐条处理，日志和计费也能独立统计。  
缺点：需要新增表、接口和页面。  
结论：推荐采用。

### 方案 C：使用通用查询日志表承载所有延时状态

优点：少建表。  
缺点：查询日志本身不可修改，延时处理需要不断更新处理状态和结果状态，会破坏“日志不可抵赖”的账务语义。  
结论：不采用。

推荐方案：方案 B。新增“精准延时查询请求”作为业务主表，日志表继续作为不可抵赖凭证。

## 5. 目标流程

### 5.1 保险公司实时查询流程

1. 保险公司进入查询页，选择“实时查询”。
2. 输入姓名、身份证号、查询接口。
3. 后台校验公司身份、公司状态、月度额度和价格。
4. 后台调用数产集团实时接口。
5. 系统将数产集团返回的数据原样返回给保险公司。
6. 系统记录实时查询日志和费用。

验收标准：

- [ ] 实时查询不再对数产集团返回数据做脱敏、分类、字段改名等加工。
- [ ] 实时查询成功、失败、未查得均有日志。
- [ ] 实时查询费用按实时服务价格入账。
- [ ] 接口返回体能保留数产集团原始字段结构。

### 5.2 保险公司精准延时查询提交流程

1. 保险公司进入查询页，选择“延时精准数据”。
2. 输入姓名、身份证号，点击查询。
3. 后台生成精准延时查询请求。
4. 页面立即展示“已提交，等待处理”，并显示请求编号、提交时间、当前状态。
5. 保险公司可以关闭或退出页面。
6. 保险公司再次进入查询页或查询记录页时，可以看到该请求最新状态。

验收标准：

- [ ] 提交后接口立即返回，不阻塞等待人工结果。
- [ ] 新请求默认状态为“查询状态=未查询，结果上传=未上传”。
- [ ] 同一公司可以看到自己提交的精准延时请求列表。
- [ ] 不同公司之间请求数据隔离。

### 5.3 平台后台处理流程

1. 平台管理/运营人员进入“精准延时查询管理”页面。
2. 列表展示：姓名、身份证号、公司名称、查询状态、结果上传、提交时间、处理人、处理时间。
3. 对“未上传”的请求显示“上传”按钮。
4. 点击“上传”进入结果处理页。
5. 处理页支持上传 Excel，并将 Excel 内容解析为可编辑明细表。
6. 处理页支持不上传 Excel，直接逐行新增结果数据。
7. 明细行支持编辑、删除。
8. 点击“确定保存”只保存草稿，不暴露给保险公司。
9. 点击“上传完毕”后，请求状态变为“查询状态=已查询，结果上传=已上传”。
10. 返回请求列表后，该条记录显示已上传。

验收标准：

- [ ] 未上传请求可进入上传页。
- [ ] Excel 导入后明细表可编辑。
- [ ] 支持手工逐行添加明细。
- [ ] 保存草稿不会让保险公司看到最终结果。
- [ ] 上传完毕后保险公司可查看结果。
- [ ] 上传完毕后仍保留操作日志，能追溯处理人和处理时间。

### 5.4 保险公司查看精准延时结果流程

1. 保险公司进入“查询记录”或查询页结果区域。
2. 对未处理请求显示“处理中/等待上传结果”。
3. 对已上传请求显示“查看结果”。
4. 如果上传的是明细数据，展示明细列表。
5. 如果上传的是空结果，展示空结果和说明信息。

验收标准：

- [ ] 未上传时不显示空白结果冒充查询完成。
- [ ] 已上传明细时能查看完整结果。
- [ ] 已上传空结果时能显示业务说明。
- [ ] 页面刷新或重新登录后状态仍正确。

## 6. 数据模型计划

### 6.1 新增：精准延时查询请求表

建议表名：`biz_delayed_query_request`

核心字段：

| 字段 | 说明 |
| ---- | ---- |
| id | 主键 |
| request_no | 请求编号 |
| company_id | 保险公司 ID |
| company_name_snapshot | 公司名称快照 |
| patient_name | 姓名 |
| id_card | 身份证号 |
| query_type | 查询类型，建议固定为 `delayed_precise` 或按具体业务再细分 |
| query_status | 查询状态：`PENDING` 未查询，`QUERIED` 已查询 |
| upload_status | 结果上传：`NOT_UPLOADED` 未上传，`UPLOADED` 已上传 |
| result_status | 结果状态：`HIT` 查得，`NO_RESULT` 未查得，`PARTIAL` 部分说明 |
| result_message | 返回给保险公司的说明信息 |
| submit_time | 保险公司提交时间 |
| request_ip | 请求 IP |
| handler_id | 处理人 |
| handler_name | 处理人姓名 |
| handled_time | 人工查询完成时间 |
| uploaded_time | 上传完毕时间 |
| remark | 内部备注 |
| create_time/update_time | 创建和更新时间 |

### 6.2 新增：精准延时查询结果明细表

建议表名：`biz_delayed_query_result`

核心字段：

| 字段 | 说明 |
| ---- | ---- |
| id | 主键 |
| request_id | 关联精准延时请求 |
| row_no | 行号 |
| hospital_name | 医院名称 |
| visit_time | 就诊时间 |
| visit_type | 就诊类型 |
| doctor_name | 医师 |
| diagnosis_result | 诊断结果 |
| insured_flag | 是否投保/参保 |
| medical_insurance_region | 医保区划 |
| insurance_type | 险种类型 |
| person_type | 人员类型 |
| first_insured_month | 首次参保年月 |
| current_insured_date | 本次参保日期 |
| suspended_insured_date | 暂停参保日期 |
| insured_org | 医保参保单位 |
| raw_json | Excel 原始行或扩展字段 JSON |
| create_time/update_time | 创建和更新时间 |

说明：字段先覆盖图三中可见列和用户描述中的“保险、五险一金、已失业但无明细”等场景；不确定字段放入 `raw_json`，避免后续 Excel 模板小变动就反复改表。

### 6.3 新增：导入批次记录

建议表名：`biz_delayed_query_import`

用于记录某个请求的 Excel 文件、导入行数、成功/失败行数和错误信息。现有 `biz_data_import_log` 可参考，但不建议直接混用，避免历史数据导入和延时请求结果上传的语义混在一起。

## 8. 页面计划

### 8.1 保险公司查询页

改造点：

- 查询类型切换保留“实时查询 / 延时精准数据”。
- 实时查询维持现有同步结果区。
- 延时精准数据提交后显示请求卡片：请求编号、提交时间、查询状态、结果上传状态。
- 延时请求列表显示“处理中 / 查看结果”。
- 已上传结果可在页面中展开查看，空结果显示说明信息。

成功标准：

- [ ] 延时查询提交后页面不再显示长期等待状态。
- [ ] 保险公司退出页面后，再进入仍能看到请求状态。
- [ ] 已处理数据有明显完成状态和查看入口。

### 8.2 后台精准延时查询管理页

新增菜单建议：业务管理 -> 精准延时查询。

列表字段：

- 公司名称
- 姓名
- 身份证号
- 查询状态
- 结果上传
- 提交时间
- 处理人

- 操作：详情、上传/继续处理、查看结果

筛选条件：

- 公司名称
- 姓名
- 身份证号
- 查询状态
- 结果上传
- 提交时间范围

成功标准：

- [ ] 平台管理/运营人员能快速定位未查询、未上传请求。
- [ ] 未上传记录显示上传按钮。
- [ ] 已上传记录不误导重复上传，可进入查看或继续修正入口。

### 8.3 后台结果上传处理页

参考图三设计，页面包含：

- 顶部请求信息：公司名称、姓名、身份证号、提交时间、当前状态。
- Excel 上传区：选择文件、导入 Excel 文件内容。
- 基础信息表单：用于展示或编辑 Excel 中识别出的人员参保信息。
- 明细表格：医院名称、就诊时间、就诊类型、医师、诊断结果、参保信息等。
- 行操作：新增、编辑、删除。
- 结果说明：支持填写返回给保险公司的说明信息。
- 操作按钮：确定保存、上传完毕、返回列表。

成功标准：

- [ ] Excel 导入成功后生成可编辑明细。
- [ ] 手动新增行无需 Excel 文件。
- [ ] 上传空结果时必须填写说明信息。
- [ ] “确定保存”和“上传完毕”语义清楚，不混用。

### 8.4 按公司查看日志页

改造方式：

- 在保险公司管理列表增加“日志”入口，或在日志管理页增加公司聚合视图。
- 点击某个公司后进入公司日志详情页。
- 页面分两个页签：实时查询日志、精准延时查询日志。
- 实时查询日志复用 `biz_query_log`。
- 精准延时查询日志读取 `biz_delayed_query_request` 及相关处理记录。

成功标准：

- [ ] 平台管理/运营人员能按公司查看两种服务的查询历史。
- [ ] 实时与延时日志分开展示，不混淆费用和状态。
- [ ] 延时日志能看到提交、人工处理、上传完成三个关键节点。

## 9. 计费与账务计划

待确认事项：

- 精准延时查询是在“提交请求时预留预算”，还是“上传完毕时确认扣费”。
- 空结果是否按未查得价格收费。
- 已查询到参保线索但无可返回明细，按查得、未查得还是特殊价格计费。

建议规则：

1. 提交精准延时请求时预留该公司该服务的最高价格。
2. 上传完毕时按 `HIT/NO_RESULT/PARTIAL` 确认实际费用。
3. 取消或无法处理时释放预留额度。
4. 所有费用确认都写入不可修改日志和费用流水。

成功标准：

- [ ] 实时查询和精准延时查询使用不同查询类型和价格配置。
- [ ] 精准延时请求未上传完毕前不会重复扣实际费用。
- [ ] 上传完毕后能进入月度账单统计。

## 10. 安全与权限计划

- 保险公司只能提交和查看本公司请求。
- 后台人工处理页面只开放给授权平台管理/运营人员。
- 身份证号在后台列表可按现有系统规范展示；导出和外部返回需另行确认是否脱敏。
- 实时查询“原样返回”与旧规则“外部数据脱敏”存在冲突，必须在编码前由业务方确认并记录。
- 精准延时结果上传完毕后才对保险公司可见。
- 查询请求和结果修改需要记录操作日志。

成功标准：

- [ ] 越权访问其他公司的请求返回 403 或空数据。
- [ ] 未授权后台账号不能进入精准延时处理页。
- [ ] 上传完毕前保险公司接口不返回草稿明细。

## 12. 最小验收用例

1. 实时查询查得数据：保险公司提交姓名身份证，系统调用数产集团接口，原样返回数据，写入实时日志和费用。
2. 实时查询未查得：系统原样返回数产集团未查得响应，写入未查得日志和费用。
3. 精准延时提交：保险公司提交姓名身份证，立即获得请求编号，状态为未查询、未上传。
4. 精准延时 Excel 上传：平台管理/运营人员上传 Excel，系统生成明细草稿，可编辑后保存。
5. 精准延时手工录入：平台管理/运营人员不上传 Excel，逐行添加明细并上传完毕。
6. 精准延时空结果：平台管理/运营人员不添加明细，填写说明后上传完毕，保险公司看到空结果和说明。
7. 保险公司异步查看：保险公司退出后重新进入，能看到请求从未上传变为已上传。
8. 公司日志查看：平台管理/运营人员点击某公司，能分别查看实时日志和精准延时日志。
9. 权限隔离：保险公司 A 无法查看保险公司 B 的延时请求和结果。
10. 账务一致：每条实时查询和每条上传完毕的精准延时查询都能进入费用统计。

## 13. 风险与待确认项

| 风险/问题 | 影响 | 建议处理 |
| --------- | ---- | -------- |
| 实时数据原样返回与旧脱敏规则冲突 | 可能影响外部数据合规 | 编码前由业务方确认，必要时保留接口级开关但默认按新需求执行 |
| 精准延时结果字段可能随 Excel 模板变化 | 频繁改表 | 固定核心字段，扩展字段存 `raw_json` |
| 空结果但有参保线索的计费口径不清 | 影响账单 | 新增 `PARTIAL` 或明确归为 `HIT/NO_RESULT` |
| 上传完毕后是否允许修改 | 影响审计 | 建议允许“修正”，但保留修改日志和版本记录 |
| 人工处理时间不确定 | 影响保险公司体验 | 页面明确显示“等待处理”，不承诺完成时间 |

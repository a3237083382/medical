# 保险公司嵌入式医疗查询页面设计

> 日期：2026-08-14  
> 状态：已确认，待实现  
> 页面源码：`insurance-embed/index.html`

## 1. 目标

将现有独立 HTML 原型改造成供保险公司嵌入自有系统的医疗查询工作台。页面独立部署，只调用本平台提供的接口，不直接访问数产集团。

当前阶段链路：

```text
保险公司系统 -> 独立嵌入页面 -> 本平台接口 -> 模拟实时数据源 / 精准延时人工处理
```

数产集团接口确定后，只替换平台内部的 `MedicalDataSource` 实现，保险公司页面和平台对外接口保持稳定。

## 2. 范围

保险公司页面负责：

- 手工输入并验证 AppKey；
- 单人实时查询和单人精准延时查询；
- Excel 批量名单导入、校验、修改和确认；
- 批量实时查询和批量精准延时查询；
- 查询状态、批次进度、历史记录和新结果提醒；
- 取消符合条件的单条记录或整个批次；
- 导出单人结果或整批结果为 Excel。

平台管理后台负责：

- 查看和筛选精准延时请求；
- 标记开始处理；
- 导入动态字段结果或手工维护结果；
- 保存草稿、上传完毕和修改已上传结果；
- 查看按公司隔离的实时与精准延时日志。

## 3. 部署与鉴权

页面独立部署，不放入 `RuoYi-Vue3/public`。运行环境通过部署配置指定平台 API 基础地址，页面源代码不写死开发地址。

所有保险公司接口使用同一种鉴权方式：

```http
X-App-Key: <company-app-key>
```

规则：

- 只使用 AppKey，不使用 AppSecret、HMAC、时间戳、Nonce 或公司登录 Token；
- AppKey 由用户每次打开页面后手工输入；
- AppKey 只保存在当前页面的 JavaScript 内存中；
- 页面刷新或关闭后不保留 AppKey；
- 不写入 Cookie、`localStorage`、`sessionStorage`、URL 或 iframe 参数；
- 页面、控制台、异常信息和服务日志不得输出完整 AppKey；
- 后端根据 AppKey 绑定公司上下文，所有查询必须附加 `company_id` 条件；
- 正式环境必须使用 HTTPS；
- 独立部署域名通过后端白名单配置 CORS，并允许 `X-App-Key` 和文件上传请求。

## 4. 页面信息架构

页面采用亮色业务系统布局：

1. 顶部栏：系统名称、接入状态、脱敏 AppKey 标识、新结果提醒和重新接入。
2. 查询工作台：服务模式与查询方式选择、表单或批量导入区、当前结果区。
3. 历史记录：单人和批次历史、筛选、状态和详情入口。
4. 详情层：单人结果、批次明细、取消操作和 Excel 导出。

查询工作台包含两组分段选择：

| 维度 | 选项 |
| --- | --- |
| 服务模式 | 实时查询、精准延时查询 |
| 查询方式 | 单人查询、批量导入 |

实时查询显示查询项目；精准延时查询不区分查询项目。

## 5. 视觉与响应式要求

- 背景使用白色或浅灰色，内容区域为白色；
- 文字使用深灰色，主色使用蓝色或蓝绿色；
- 成功、处理中、失败分别使用绿色、橙色和红色；
- 不使用大面积深色背景、强渐变和过重阴影；
- 表单、表格、状态标签和操作按钮优先保证扫描效率；
- 桌面布局可并列展示输入和结果，窄 iframe 自动改为上下布局；
- 固定格式控件使用稳定尺寸，动态文本不得撑破容器；
- 在 Chrome、Edge、常见 WebView 和 iframe 中不得出现遮挡或横向溢出。

## 6. 单人实时查询

输入字段为姓名、身份证号和实时查询项目。页面完成基本校验后调用平台单人实时接口。

处理顺序：

```text
参数校验 -> AppKey/公司校验 -> 额度预留 -> 数据源查询 -> 结果判定 -> 日志与计费确认 -> 返回结果
```

当前使用模拟数据源。未来数产集团返回的业务字段由平台原样透传，不做摘要、字段重命名或业务加工；页面使用通用动态字段视图安全展示结果。

查询结果分为：

- `HIT`：查得，按价格规则收费；
- `NO_RESULT`：未查得，不收费；
- `FAILED`：失败或超时，不收费。

每次查询都写入不可删除的查询日志。失败不得保留预算预留金额。

## 7. 单人精准延时查询

保险公司只填写姓名和身份证号。提交后立即创建请求并返回请求编号、提交时间和当前状态，页面不等待人工处理。

如果同一公司、同一姓名和身份证号已有未完成请求，服务端返回原请求并设置 `reused=true`，不创建重复记录。已完成、失败或取消的记录不阻止重新提交。

平台人员保存草稿时，保险公司只能看到处理中状态；只有执行“上传完毕”后，最终结果才可查看并进入计费判断。

结果规则：

| 结果 | 是否展示 | 是否收费 |
| --- | --- | --- |
| `HIT` | 展示结果明细 | 收费 |
| `NO_RESULT` | 展示未查得说明 | 不收费 |
| `HINT_ONLY` | 只展示结果说明 | 不收费 |
| `FAILED` | 展示失败说明 | 不收费 |

## 8. 批量导入与可编辑预览

支持 `.xlsx` 和 `.xls`，不支持 `.csv`。每个批次最多 500 人，必填列为姓名和身份证号。

Excel 上传后先解析为预览数据，不创建正式批次。预览行包含原始值、当前值、校验状态和错误说明。

保险公司可以：

- 修改姓名和身份证号；
- 新增一行；
- 删除单行或批量删除；
- 恢复原始导入值；
- 重新校验；
- 仅查看错误行。

校验覆盖空值、18 位身份证格式、批次内重复、文件类型、文件结构、解析异常和 500 人限制。存在错误时禁止确认提交。Excel 原文件不修改，以页面最终确认的数据为准。

## 9. 批量实时查询

批次确认后，由后端创建批次和人员明细。浏览器不直接并发调用单人接口。

每个批次始终最多同时执行 5 条：先启动第 1 至 5 条，其中任意一条进入终态后立即补充下一条。单条失败、超时或取消不影响其他记录。

页面展示总人数、待处理、处理中、查得、未查得、失败、已取消、完成进度和总费用。

## 10. 批量精准延时查询

批量提交后，每个人形成独立精准延时请求。存在未完成重复请求时复用原请求，并在批次明细中标记 `reused=true`。

平台后台可以按批次或单人处理。保险公司可以离开页面，之后通过历史记录或新结果提醒查看进度。只有上传完毕的结果可查看和计费。

## 11. 状态模型

### 11.1 处理状态

| 状态 | 含义 | 可否取消 |
| --- | --- | --- |
| `PENDING` | 尚未开始查询或人工处理 | 可以 |
| `PROCESSING` | 实时查询执行中或平台人员已开始处理 | 不可以 |
| `COMPLETED` | 已产生最终结果 | 不可以 |
| `FAILED` | 查询执行失败 | 不需要取消 |
| `CANCELLED` | 已从待处理队列移除 | 不可以重复取消 |

### 11.2 上传和业务结果状态

- 上传状态：`NOT_UPLOADED`、`UPLOADED`；
- 结果状态：`HIT`、`NO_RESULT`、`HINT_ONLY`、`FAILED`、`CANCELLED`；
- 查看状态：`UNREAD`、`READ`。

批次状态由明细汇总得到：`PENDING`、`PROCESSING`、`COMPLETED`、`FAILED`、`PARTIAL_FAILED`、`PARTIAL_CANCELLED`、`CANCELLED`。

## 12. 取消规则

保险公司可取消单条记录或整个批次。只有处理状态为 `PENDING` 且上传状态为 `NOT_UPLOADED` 的记录可以取消。

平台人员点击“开始处理”或实时任务开始执行后，状态必须原子更新为 `PROCESSING`，之后不能取消。

取消成功后：

- 状态变为 `CANCELLED` 并从等待队列移除；
- 不执行查询、不收费，允许以后重新提交；
- 保留原始请求记录及已取消状态；
- 不记录取消人、取消时间和取消原因；
- 不创建单独的取消日志。

取消整个批次时，仅取消仍满足条件的明细；其余明细继续处理或保留结果，批次显示已取消或部分取消。

## 13. 历史、提醒与导出

历史记录覆盖单人实时、批量实时、单人精准延时和批量精准延时。列表中的身份证号必须脱敏，详情权限由当前 AppKey 对应公司决定。

AppKey 验证成功后，页面检查当前公司已完成但未查看的精准延时结果。页面打开期间定时轮询，用户也可手动刷新。查看后标记为 `READ`，但结果仍可从历史记录再次打开。

导出格式统一为 `.xlsx`：

- 单人导出包含当前人员基本信息、查询状态、费用和实际结果；
- 整批导出包含批次内所有人员的状态、费用和结果；
- 动态结果字段必须保留；
- 批次仍有 `PENDING` 或 `PROCESSING` 明细时不能整批导出；
- 终态记录均保留在整批导出中，没有结果时写明状态和说明。

## 14. 数据模型边界

详细数据库设计见 `docs/保险公司嵌入式查询数据库设计.md`。

下一步数据库设计至少需要表达以下实体，最终表名在数据库设计阶段确定：

- 查询批次：公司、服务模式、查询项目、批次状态、统计数量和费用汇总；
- 查询请求明细：批次、公司、人员信息、处理状态、上传状态、结果状态和费用快照；
- 动态查询结果：请求明细、动态字段 JSON、结果说明和上传信息；
- 已查看状态：请求明细的 `UNREAD/READ` 状态；
- 现有 `biz_query_log`：继续作为不可修改的查询与计费凭证，不承担可变工作流状态。

取消记录只保留请求本身及 `CANCELLED` 状态，不新增取消审计字段。

## 15. 并发与事务

- 批量实时任务按批次限制最多 5 条 `PROCESSING`；
- 任务领取、开始处理、取消和上传完毕必须使用条件更新或锁避免竞争；
- 额度预留、结果确认、费用快照和日志写入处于同一事务边界；
- 失败、超时和取消不得产生收费；
- 精准延时只有上传完毕后才进行最终计费；
- 单条失败不能回滚整个批次。

## 16. 原型清理

实现阶段从 `insurance-embed/index.html` 删除：

- 硬编码演示 AppKey；
- 查得、未查得和异常演示开关；
- `MOCK_DATA`；
- 本地假 `request()`；
- 固定模拟延迟；
- 只检查 AppKey 长度的假验证；
- 精准延时立即返回模拟结果的逻辑。

模拟数据移至后端 `MedicalDataSource`，独立页面只通过真实 HTTP 接口获取数据。

## 17. 验收原则

- 所有保险公司数据按 AppKey 对应公司隔离；
- 单人和批量、实时和精准延时四条流程均闭环；
- 批量最多 500 人，每批实时并发不超过 5；
- 导入数据可修改并重新校验；
- 取消、提醒、历史、计费和两类 Excel 导出符合已确认规则；
- 页面刷新后不保留 AppKey；
- 页面为亮色并适配独立部署、iframe 和 WebView；
- 页面不再包含前端模拟业务数据。

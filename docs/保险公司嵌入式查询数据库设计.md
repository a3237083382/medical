# 保险公司嵌入式查询数据库设计

> 日期：2026-08-17  
> 状态：迁移脚本已编写并完成静态检查，尚未执行  
> 数据库：MySQL 8.0 / `ry_vue`

## 1. 设计目标

数据库需要同时支撑：

- 单人实时查询与单人精准延时查询；
- 最多 500 人的批量实时与批量精准延时查询；
- 每个实时批次最多 5 条并发执行；
- 精准延时未完成请求复用；
- 单人取消、整批取消和部分取消；
- 动态 Excel 字段结果、草稿、上传完毕和修改；
- 统一历史、未读提醒、单人/整批 Excel 导出；
- 月度额度预留、最终计费和不可修改查询日志。

工作流状态与查询日志必须分离。工作流记录允许按规则发生状态迁移；`biz_query_log` 继续作为不可修改、不可删除的最终查询和计费凭证。

## 2. 已有数据库基线

- 额度与账单：`biz_monthly_usage`、`biz_monthly_bill`、`biz_monthly_bill_detail`；

## 4. 为什么批次成员必须独立建表

精准延时批量提交时，如果同一公司、姓名和身份证号已有未完成请求，需求要求复用原请求而不是新建请求。一个查询请求因此可能同时出现在原单人入口和后续批次中，或者被多个批次引用。

如果直接把 `batch_id` 放在查询请求上，会出现以下问题：

- 一个请求无法属于多个批次；
- 取消后加入批次的复用记录可能误取消原始请求；
- 同一查询可能被重复计费；
- 批次行顺序和复用标记无法独立保存。

因此使用 `biz_medical_query_batch_item` 建立批次与请求的多对一关联。取消复用成员只取消关联，不取消原始请求；只有非复用成员且没有其他有效引用时，才允许同时取消底层请求。

## 5. 查询批次表

表名：`biz_medical_query_batch`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint | PK, auto increment | 主键 |
| `batch_no` | varchar(32) | NOT NULL, UNIQUE | 对外批次编号 |
| `company_id` | bigint | NOT NULL | AppKey 对应公司 |
| `service_mode` | varchar(16) | NOT NULL | `REALTIME/DELAYED` |
| `query_type` | varchar(50) | NULL | 实时查询项目，延时为空 |
| `batch_status` | varchar(24) | NOT NULL | 批次状态 |
| `total_count` | int | NOT NULL default 0 | 总人数，最大 500 |
| `pending_count` | int | NOT NULL default 0 | 待处理数 |
| `processing_count` | int | NOT NULL default 0 | 处理中数 |
| `completed_count` | int | NOT NULL default 0 | 完成数 |
| `hit_count` | int | NOT NULL default 0 | 查得数 |
| `no_result_count` | int | NOT NULL default 0 | 未查得数 |
| `failed_count` | int | NOT NULL default 0 | 失败数 |
| `cancelled_count` | int | NOT NULL default 0 | 已取消数 |
| `total_fee` | decimal(12,2) | NOT NULL default 0 | 本批次实际费用汇总 |
| `request_ip` | varchar(50) | NULL | 批次提交 IP |
| `create_time` | datetime | NOT NULL | 创建时间 |
| `complete_time` | datetime | NULL | 进入终态时间 |
| `update_time` | datetime | NULL | 最近汇总时间 |

索引：

- 唯一索引 `uk_medical_batch_no(batch_no)`；
- 列表索引 `idx_medical_batch_company_time(company_id, create_time)`；
- 调度索引 `idx_medical_batch_status(batch_status, create_time)`；
- 公司状态索引 `idx_medical_batch_company_status(company_id, batch_status)`。

计数字段作为查询优化缓存，由服务层在明细状态变化的同一事务中重新汇总或原子增减，不由前端提交。

批次状态按以下优先级汇总：

1. 全部有效成员为 `PENDING`：`PENDING`；
2. 任一有效成员为 `PENDING/PROCESSING`：`PROCESSING`；
3. 全部成员为 `CANCELLED`：`CANCELLED`；
4. 全部非取消成员为 `FAILED`：`FAILED`；
5. 终态中同时存在取消和非取消成员：`PARTIAL_CANCELLED`；
6. 终态中存在失败且存在成功完成成员：`PARTIAL_FAILED`；
7. 其余全部正常完成：`COMPLETED`。

## 8. 动态结果表

表名：`biz_medical_query_result`

每个查询请求只保存一个当前有效结果。平台修改已上传结果时更新当前结果并增加版本号，不在本阶段新增完整历史版本表。

上传完毕时结果状态和计费日志已经固化。后续修改只允许修正 `column_schema`、`result_data`、`result_summary` 和修改说明，不允许改变请求的 `result_status`、费用快照或不可修改查询日志。

## 10. 状态初始值与迁移

### 10.1 实时请求

```text
创建：PENDING / NOT_UPLOADED / null / READ
开始：PROCESSING
查得：COMPLETED / UPLOADED / HIT / READ
未查得：COMPLETED / UPLOADED / NO_RESULT / READ
异常：FAILED / NOT_UPLOADED / FAILED / READ
取消：CANCELLED / NOT_UPLOADED / CANCELLED / READ
```

### 10.2 精准延时请求

```text
提交：PENDING / NOT_UPLOADED / null / READ
开始处理：PROCESSING / NOT_UPLOADED
保存草稿：PROCESSING / NOT_UPLOADED
上传查得：COMPLETED / UPLOADED / HIT / UNREAD
上传未查得：COMPLETED / UPLOADED / NO_RESULT / UNREAD
上传提示：COMPLETED / UPLOADED / HINT_ONLY / UNREAD
失败：FAILED / NOT_UPLOADED / FAILED / READ
取消：CANCELLED / NOT_UPLOADED / CANCELLED / READ
```

只有 `COMPLETED + UPLOADED + UNREAD` 的精准延时请求进入新结果提醒。

## 11. 取消与复用事务规则

### 11.1 非复用请求

取消条件更新必须同时检查：

```text
process_status = PENDING
upload_status = NOT_UPLOADED
version = 客户端读取版本
```

更新成功后释放已预留额度，并将状态改为 `CANCELLED`。不保存取消人、取消时间或取消原因。

### 11.2 复用批次成员

取消 `reused_flag='1'` 的成员时，只把 `biz_medical_query_batch_item.item_status` 改为 `CANCELLED`，不能修改原请求状态。

取消非复用成员时，如果该请求没有其他有效批次引用且不是单人入口，才同时取消底层请求。批次汇总只统计当前批次的有效成员。

## 12. 批量实时并发约束

调度器领取任务时，以批次为单位统计 `PROCESSING` 请求。只有当前数量小于 5 时，才按 `row_no` 领取新的 `PENDING` 成员。

推荐使用条件更新领取：

```text
PENDING -> PROCESSING
同时写 process_start_time 并增加 version
```

领取、执行和完成不能放在一个长事务中。领取事务应快速提交；外部查询结束后使用独立事务写结果、确认费用、写查询日志并更新批次汇总。

## 13. 计费与日志事务

- 创建请求时保存价格配置来源和最大预留金额；
- 需要额度控制时，在提交或任务开始前预留月度额度；
- `HIT` 按查得价格确认费用；
- `NO_RESULT`、`HINT_ONLY`、`FAILED`、`CANCELLED` 最终费用为 0；
- 失败和取消必须释放预留额度；
- 精准延时只有上传完毕后才确认费用和写最终查询日志；
- 复用请求只计费一次；
- 结果、额度确认、费用快照、日志和请求终态在同一事务内写入；
- 批次总费用只汇总本批次非复用且实际收费的请求。

## 14. 数据隔离与敏感信息

- 所有批次、请求和结果查询必须先绑定当前 AppKey 对应 `company_id`；
- 详情不能只按 `request_no` 查询，必须同时检查 `company_id`；
- 列表与提醒中的身份证号由服务层脱敏；
- AppKey 不写入任何新增表；
- 查询结果 JSON 只在有权限的详情和导出接口中返回；
- `biz_query_log.query_params` 对姓名和身份证号使用脱敏快照；
- Excel 导出和动态 JSON 读取必须受公司隔离约束。

## 15. 外键与删除策略

现有业务表未统一使用数据库外键。新增表保持同一风格，通过索引和服务层事务维护引用关系，避免迁移和线上数据清理受外键阻塞。

业务数据不提供物理删除：

- 批次、请求、成员和结果均不提供删除接口；
- 取消通过状态表达；
- 查询日志继续由触发器禁止更新和删除；
- 后续如需数据保留期限，单独制定归档方案，不在本阶段直接删除医疗结果。
